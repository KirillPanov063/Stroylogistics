# Stroylogistics

Техническое задание: Система учета заявок на доставку и забор контейнеров
1. Общие сведения
1.1. Назначение системы
Разработка веб-приложения для автоматизации процесса учета заявок на доставку и забор контейнеров с системой разграничения прав доступа и автоматической нумерацией заявок.

1.2. Цели создания
Автоматизация процесса обработки заявок

Учет и контроль выполнения заявок

Разграничение прав доступа между пользователями

Упрощение процесса создания и отслеживания заявок

1.3. Целевая аудитория
Менеджеры по логистике

Администраторы системы

Водители

Клиенты компании

Телефон (обязательное)

Валидация уникальности email

Автоматическое присвоение роли "user" новым пользователям

Автоматический вход после успешной регистрации

Поля формы входа:

Электронная почта

Восстановление пароля через email

2.2. Модуль управления заявками
2.2.1. Создание заявки
Автоматическая генерация номера заявки (инкремент на 1 от последней заявки)

Поля формы создания заявки:

Номер заявки (автоподстановка, только для чтения)

Адрес забора контейнера (обязательное, текстовое поле)

Телефон заказчика (обязательное, валидация формата телефона)

Телефон встречающего (обязательное, валидация формата телефона)

Форма оплаты (обязательное, выпадающий список):

По счету

Перевод на карту

Наличные

Сумма оплаты (обязательное, числовое поле)

Выбор водителя (обязательное, выпадающий список из доступных водителей)

Дополнительные комментарии (необязательное, текстовое поле)

Валидация всех обязательных полей перед сохранением

Для администраторов: редактирование любых заявок

Возможность изменения всех полей заявки

Ведение истории изменений

Черновик - заявка создана, но не отправлена на обработку

В обработке - заявка принята в работу

Назначен водитель - заявка назначена конкретному водителю

В пути - водитель выехал на забор

Выполнено - заявка завершена

Отменено - заявка отменена

5. Бизнес-логика
5.1. Автоматическая нумерация заявок
Нумерация начинается с 1

Каждая новая заявка получает номер на 1 больше предыдущей

Номера не должны повторяться

При удалении заявки номер не переиспользуется

Реализация через последовательность в PostgreSQL

5.2. Правила доступа к заявкам
Пользователь может видеть и редактировать только свои заявки

Администратор видит и может редактировать все заявки

Заявка при создании привязывается к ID пользователя

Проверка прав доступа на уровне middleware

5.3. Валидация данных
Телефоны: российский формат (+7 XXX XXX-XX-XX)

Email: стандартная валидация формата

Сумма оплаты: только положительные числа

Обязательные поля должны быть заполнены

Валидация на фронтенде и бэкенде

6. API Эндпоинты
6.1. Аутентификация
POST /api/auth/register - Регистрация

POST /api/auth/login - Вход

POST /api/auth/logout - Выход

POST /api/auth/refresh - Обновление токена

6.2. Заявки
GET /api/orders - Список заявок (с фильтрами)

GET /api/orders/:id - Получить заявку

POST /api/orders - Создать заявку

PUT /api/orders/:id - Обновить заявку

DELETE /api/orders/:id - Удалить заявку

6.3. Водители
GET /api/drivers - Список водителей

POST /api/drivers - Создать водителя (admin)

PUT /api/drivers/:id - Обновить водителя (admin)

DELETE /api/drivers/:id - Удалить водителя (admin)

6.4. Пользователи
GET /api/users/profile - Профиль текущего пользователя

GET /api/users - Список пользователей (admin)

PUT /api/users/:id - Обновить пользователя (admin)
